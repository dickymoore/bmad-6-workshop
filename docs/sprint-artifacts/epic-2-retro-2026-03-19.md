## What Went Well

- The team extended one canonical dashboard model instead of creating parallel UI-specific state paths. That kept the public route coherent across live data, trust, disruption, degradation, and update continuity work.
- Each story built on the previous one with disciplined scope boundaries. Epic 2 did not collapse into an uncontrolled rewrite of Epic 1.
- The review loop was effective. High-severity issues around runtime truthfulness, fallback honesty, and live-update semantics were caught and fixed before the epic closed.
- Automated coverage matured in the right places: unit, live-path, and smoke tests now protect behavior that matters to a calm public display rather than only field presence.
- Verification artifacts improved. Story 2.5 added explicit live-reading notes instead of treating venue-scale and reduced-motion behavior as implied.

## Challenges And Growth Areas

- Boundary truth was the hardest recurring problem. Several fixes were needed because fallback, fixture, or compatibility paths initially overstated certainty.
- Public calmness is easy to regress accidentally. The team repeatedly had to correct wording, labels, and update summaries that drifted toward implementation truth without fully matching visitor-facing truth.
- Artifact synchronization lagged behind code in a few places. Story records, file lists, and sprint tracking needed cleanup after review.
- The repo still lacks a prior-retrospective habit. Epic 1 closed without a saved retrospective, so Epic 2 had no continuity baseline to measure against.

## Story-Level Patterns

### Common Success Pattern

The strongest implementation pattern was:

1. derive meaning in server or contract layers
2. shape it once in the presenter
3. keep public components thin
4. lock the behavior with targeted tests

That pattern held through all five stories and is a repeatable strength for Epic 3.

### Common Struggle Pattern

The most common struggle was honest negative-path modeling. Review findings repeatedly surfaced the same category of risk:

- static or fallback behavior appearing more current than reality
- synthetic trend or trust signals without evidence
- unavailable data inheriting live-state semantics
- UI summaries describing current state instead of actual change deltas

This was not a people problem. It was a systems problem: the product’s hardest work lives in preserving truthfulness when live evidence is incomplete.

## Key Insights

1. Calm public displays need stricter truth rules than typical dashboards. If live evidence weakens, the UI must narrow confidence immediately and locally.
2. Fallback behavior is product behavior, not implementation plumbing. The fallback path needs the same design rigor and test coverage as the happy path.
3. Presenter-level semantics are paying off. The more meaning stays canonical, the less risk there is of accidental drift between stories.
4. Epic 3 should inherit Epic 2’s readiness and source-status model directly. A second ops-only truth model would create avoidable divergence.
5. Retrospective hygiene itself is now a process gap to close. The project needs saved retrospectives at epic boundaries so lessons compound instead of resetting.
