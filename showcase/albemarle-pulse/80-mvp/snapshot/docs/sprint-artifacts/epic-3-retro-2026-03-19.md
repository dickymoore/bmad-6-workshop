## What Went Well

- Epic 3 preserved one canonical model for both public and operator-facing truth. Readiness, degraded impact, maintenance actions, and recovery all stayed grounded in the same snapshot and response metadata.
- The public and ops route separation held. The team added meaningful operator capabilities without leaking maintenance affordances into the visitor-facing display.
- Review feedback kept improving the product in the highest-risk areas. Action-result honesty, degraded-scope clarity, carried-forward recovery semantics, and stale-state wording all tightened before the epic closed.
- Negative-path behavior got first-class treatment. Denied access, degraded inputs, failed refreshes, and cold-start recovery were all tested as product behavior rather than treated as backend edge cases.
- Epic 2’s contract-first pattern held up well. Focused server helpers, thin routes, and presenter/view-model boundaries scaled cleanly into ops and recovery work.

## Challenges And Growth Areas

- Artifact synchronization still lagged behind implementation in places. The Epic 2 retro called this out, and Epic 3 still left at least one story artifact in a stale `review` state after the epic had effectively closed.
- The team repeatedly had to guard against overclaiming certainty. The risk shifted from public-display fallback honesty in Epic 2 to ops-readiness, action-result, and restart-recovery honesty in Epic 3, but the core quality problem stayed the same.
- Ops work increases the temptation to build parallel status systems. Epic 3 avoided that trap, but several stories explicitly had to reinforce the rule to reuse the public snapshot model rather than invent new ops-only semantics.
- Deployment and stakeholder acceptance remain less evidenced than repository validation. The code and tests are strong, but repo artifacts still do not show a separate formal venue release or sign-off checkpoint.

## Story-Level Patterns

### Common Success Pattern

The strongest Epic 3 pattern was:

1. reuse an existing server truth model
2. derive calm operator-facing meaning in focused server helpers
3. render it through a thin ops shell
4. protect the behavior with negative-path regression coverage

That pattern appears in all five stories and should remain the default for future venue operations work.

### Common Struggle Pattern

The most common struggle was semantic drift under non-happy paths. Review notes across the epic show repeated risk around:

- action outcomes sounding more certain than the data justified
- degraded diagnostics overstating healthy areas
- recovery reads appearing fully current after restart
- story artifacts lagging behind the final implementation state

This was not a tooling failure. It was the natural pressure point of a product whose main promise is calm, truthful public service under imperfect conditions.

## Key Insights

1. The ops surface is successful because it is not a separate product. It works only when it stays downstream of the same public snapshot semantics.
2. Recovery is a trust problem, not just an availability problem. A usable carried-forward screen after restart is valuable only if it is labeled honestly until fresh live publication resumes.
3. Local-only maintenance controls can stay lightweight if they reuse the current health pipeline rather than inventing new control paths.
4. Negative-path coverage is now a durable team strength. Epic 3 treated denied access, degraded signals, failed maintenance actions, and cold starts as core product states.
5. Process follow-through improved, but artifact-sync discipline still needs to move from intention to habit.
